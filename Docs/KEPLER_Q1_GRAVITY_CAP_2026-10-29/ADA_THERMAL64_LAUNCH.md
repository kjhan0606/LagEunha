# Early thermal64 Q1 on Ada

The original single-precision eta=.06 Ada branch completed and passed its t=.825 core screen, but had about 18 times larger disk absolute entropy change than the uncapped short comparison. To test whether thermal precision changes this result without waiting for the H200 quota, a distinct thermal64 candidate is running on the authorized `lageunha` Ada GPU. Its parent PID is **1190592**, and the actual native `eunha2.exe` PID was **1190678** at launch verification. GPU UUID is `GPU-42b3367f-1df7-2b2d-7961-7781c87b022d`.

The candidate reads the already preserved native eta=.06 checkpoint at t=.0015284035789018555, SHA256 `0f60d80dec2668a7e53a6e99ec84760af824ed70fb7a868ddd605fe53ffe11bc`, and reaches t=.4125. This is a different thermal arithmetic branch from the completed single-precision reference, not a restart or replay of the running reference; it does not start from a newly generated t0 state. The same 90,352 IDs and fixed masses, W0, no steering, Re=infinity and wall configuration apply. The exact candidate executable SHA256 is `ff3ae9b86c65e86a28dfe246a33186e9387361ee54c83439bb17bc52f85e317a`. The root and logs are `/gpfs/kjhan/LagForce/Kepler_Q1_Thermal64Early_Ada_20261029`; `contract.json`, `inputs.sha256`, `run.sh`, `chain.sh` and the actual CUDA log record the effective settings.

After successful native exit, the finite chain checks the 28 existing state gates, independent polygon geometry, a preregistered core screen and thermal64 payload, then starts exact t=.825 from that accepted thermal64 checkpoint in `/gpfs/kjhan/LagForce/Kepler_Q1_Thermal64EarlyTo0825_Ada_20261029`. The driver verifies frozen input hashes and refuses continuation on failure. Only one native full snapshot per stage is planned, about 100 MiB combined plus logs and audit files; no full-particle TSV is requested. Completion of this finite diagnostic does not constitute t6.5, t600 or multi-rank validation.

The semantically identical queued H200 parent **439903** and its afterok dependent **439950** were cancelled while still pending, avoiding duplicate work; H200 jobs 439883 and 440010 remain separate. The scheduler's prior 21:53 start time was only an estimate, not a guarantee. The first manual launch did not start because a PID-file check raced its creation; the second exited during module initialization before starting the solver because `set -u` encountered an unset Slurm variable. Those failed launch receipts remain as `chain.initial_failed.pid`, `chain.lmod_failed.pid`, and `chain.lmod_failed.log`. The corrected third launch was verified by its live process, GPU use, native accepted steps and zero floor/dual/entropy injection counters. No earlier physical checkpoint was modified.
